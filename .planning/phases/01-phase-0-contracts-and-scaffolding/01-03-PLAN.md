Decision coverage:
- D-22: unknown caller/peer SAE, wrong master, wrong slave, and wrong ownership reject before key release.
- D-23: `enc_keys` stores or emits ownership and availability metadata.
- D-24: `dec_keys` verifies caller slave SAE, path master SAE, requested `key_ID`, and availability.
- D-25: successful `dec_keys` consumes the key so repeat retrieval fails.
- D-38: required e2e invariant is `key_hex_alice == key_hex_bob`.
- D-42: Phase 0 acceptance requires docs, internal consistency, scaffolds, and parseable Compose when available.
- D-43: `docs/test-plan.md` includes e2e key equality, one-time `dec_keys`, wrong SAE/ownership rejection, exact ETSI JSON names, and ETSI base64 to SKIP hex conversion.
- D-44: Phase 0 does not require containers to start successfully or provide working service logic.

<threat_model>
Scope: verification and security documentation only; no authentication, TLS, key storage, entropy, or endpoint implementation is introduced.

Assets:
- Accuracy of Phase 0 acceptance criteria.
- Safety of future key material handling requirements.
- Explicit non-production scope.

Threats and mitigations:
- HIGH: Security docs imply production-safe key handling. Mitigate by stating local-only, simulated key material, no production readiness, and deferred TLS/mTLS/authentication.
- HIGH: Verification accepts superficial docs while missing core protocol invariants. Mitigate by requiring checks for key equality, one-time `dec_keys`, wrong SAE/ownership rejection, public ETSI JSON names, and base64-to-hex conversion.
- HIGH: Test plan treats container startup or working services as Phase 0 acceptance. Mitigate by making Compose parsing optional and explicitly excluding service startup from Phase 0 acceptance.
- MEDIUM: Logs expose full simulated key material. Mitigate by requiring future logs to use fingerprints and never full `key` or key material values.
- MEDIUM: Entropy language overstates the mock. Mitigate by documenting entropy as simulated/contract-level until implementation tests exist.

Blockers: HIGH threats are mitigated by explicit acceptance criteria and security disclaimers.
</threat_model>
