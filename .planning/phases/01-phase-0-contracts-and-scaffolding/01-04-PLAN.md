- Compose services: `kme-mock`, `keyprovider-a`, `keyprovider-b`, `encryptor-a-sim`, `encryptor-b-sim`.
- Compose volumes: `keyprovider_a_data`, `keyprovider_b_data`.

Decision coverage:
- D-07: KeyProvider-A and KeyProvider-B are represented by one configurable implementation under `services/keyprovider/`.
- D-08: `infra/docker-compose.yml` instantiates KeyProvider-A and KeyProvider-B separately with distinct configuration, ports, and SQLite storage paths or volumes.
- D-09: Phase 0 service bases are `services/kme-mock/`, `services/keyprovider/`, and `services/encryptor-sim/`; Compose instantiates A/B roles rather than duplicating source directories.

<threat_model>
Scope: Local Docker Compose skeleton and placeholder service directories; containers are not required to start and no full service logic is created.

Assets:
- Provider independence in runtime configuration.
- Correct local topology for future implementation.
- Avoidance of accidental production claims in scaffold.

Threats and mitigations:
- HIGH: Compose introduces shared provider state, hiding synchronization mistakes. Mitigate by using `keyprovider_a_data` and `keyprovider_b_data` as separate volumes and by assigning each provider its own SQLite path under its own mounted `/data`.
- MEDIUM: Placeholder commands look like real services. Mitigate with explicit placeholder text in commands and service READMEs stating that Phase 0 does not implement API logic.
- MEDIUM: Namespace secret is represented as a real production secret. Mitigate by using a clearly non-production placeholder value and documenting that it must be replaced and not logged later.
- LOW: Compose parse check fails because directories are missing. Mitigate by creating all service directories before verification.

Blockers: The HIGH shared-state threat is mitigated by separate named volumes and acceptance criteria that reject shared provider storage.
</threat_model>
